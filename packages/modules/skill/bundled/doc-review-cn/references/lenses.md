# 镜头详解：取证手法与真实战例

每个镜头三段：**查什么 / 怎么取证 / 真实战例**（战例来自三场实战：一份实施方案书的七轮深审、一份核心计划的十一轮复审、一份设计主文档的八轮审查加机械化终验）。动手前读本镜头小节，按手法执行，不要凭印象。

---

## §1 事实时效

**查什么**：文档头部或约束区声明的「基线」类事实——commit hash、测试数、版本号、批次号、日期——是否仍然真实；文档内部是否自相矛盾（引用了比自己声明的基线更新的东西）。

**怎么取证**：
- `git log --oneline -N` 对照文档声明的基线 hash；`pnpm test`（或该仓库等价物）数实际测试数。
- **计数类 grep 排除测试文件**（限定 `src/index.ts` 或加 `--exclude="*.test.ts"`）——真实事故：工具数把 `index.test.ts` 里的夹具 `t__x`/`t__y` 计入，9 之误恰为 7 之真；「现状」类断言的取证命令本身要先审计样本面。
- 文内 grep 引用到的 commit hash / 日期，与 `git log --format="%h %ad %s" --date=format:"%m-%d %H:%M"` 的真实时间比对。
- 注意「基线陈旧」的两类：一类是文档落后于现实（改了代码忘更新文档），一类是**文档自我矛盾**（正文引用了头部基线之后的 commit——说明头部没跟上）。

**战例**：方案书声明基线 `master = 5b51cf1，398 测试`，但正文进度注记引用了更晚的 `bdf2a19`（banner，+4 测试）——文内自相矛盾。修复：基线更新为 75d4ce9/402，并预测链（T0→T7 各任务测试数）整体平移。另一处「181 家厂商目录」实测磁盘缓存为 221——数字型事实同样会陈旧。

## §2 结构完整性

**查什么**：编号体系完备（有 II–V 就该有 I）；节标题与节内容一致（标题说 B5–B8、正文却有 B10/B11）；同一事物不在互斥的两处登记（「M4 范围内」和「不在 M4 排期」同时出现即矛盾）；条目在总表与分区的互指完整。

**怎么取证**：
- `grep -n "^#\|^##\|^###"` 拉全部标题，人工过编号序列。
- 对总表/清单里的每个编号 grep 全文，确认恰好一处权威定义（引用处不算）。
- 找「双重登记」：同一关键词（如某条目名）在「范围」和「范围外」两章都出现，删一处留权威位。

**战例**：文档有 Part II/III/IV/V 却无 Part I（总纲无编号）；批 B 标题写（B5-B8）但正文含后补的 B10/B11；C6 条目同时出现在 M4-2 批次清单和「条件触发项（不主动立项）」台账——in-scope 与 out-of-scope 矛盾，删批内留台账。

## §3 编号与交叉引用

**查什么**：决策号（D12 之类）、章节号（§6.7 之类）、别名缩写、外部文档指针——每个都可解析、指向正确、且不与其他编号体系撞车。

**怎么取证**：
- 文中出现的每个决策号/规则号，到权威登记册（如 design-decisions.md）grep 该号，**核对语义匹配**而不只是存在。警惕从对话记忆带出的伪引——登记册里 grep 不到、或 grep 到但主题完全不同，都算伪引。
- 章节号引用：`grep -n "^## \|^### "` 拉被引文档的目录，确认所引内容真在该节。特别当心**一项变更散布多节**（某契约同时写在 §6.2 伪码、§6.5 条款、§6.7 教义三处——只引两处就会漏改第三处）。
- 收口时升级为**机械化全覆盖**（不是抽样）：提取文中全部决策号逐号 grep 登记册、提取全部 § 引用逐个对位目录——某设计文档终验以此法一次校验 25 种小节引用全合法、D1–D28 全命中，此后定为固定工序。
- 缩写/简称：首次出现处 grep 是否有定义（「（下文简称 X）」）。
- 撞号：两套编号体系在同一文档并用（本文 B 系 vs 外部底稿 B 系）时，给弱势体系加前缀（「底稿 B6」）。另防**同号不同义**：登记册自己也可能出过双批次同号事故——发现语义矛盾时以 git 历史复核谁先谁后。
- 引号内的「引文」：到原文逐字比对。转述就别用引号——引号暗示逐字。

**战例**（七轮中最大的一窝）：D12–D16 五处决策号引用全部与登记册对不上（实际 D13=审批语义、D16=L2 签名 spike），且被引的规格文件自己注明「关联决策：未登记」——伪引全部清除。§6.7 修订实际是 §6.2 伪码 + §6.5 双写条款 + §6.7 教义三节，初版只引了一节。A1/A2 两个条目号全文无定义（已删备忘录的遗产）且与外部底稿编号撞车，统一改为权威的 D45/D46。

## §4 语言通顺与语义歧义

**查什么**：悬空指代（指向只在历史对话/已删文件里存在的东西）；语义歧义句（一个词两种读法、其中一种是错的）；不会老化的表述。

**怎么取证**：
- grep 文档里的「问题①②③」「第 N 批登记」「见 memo」类标记——若其指向物在仓库中不存在（被删文件、纯会话上下文），替换为可验证锚点（决策号、代码注释原文、file:line）或删除。
- 歧义句自测：「升级为 X」是改造旧的还是新增？「与 T3 无冲突」的 T3 是本文 T3 还是别的计划的 T3？发现两读时改成单读。
- 口语黑话（「喂盘」「扩门」「止血」）若上下文不足以自释，补足或替换。

**战例**：「modelOverride 是内存态——走查问题④」——问题编号只存在于已压缩的会话里，替换为代码注释原文「D38 定案『会话内存态不落盘』」（file 锚点可验证）。「审批选项『始终允许』升为写规则落盘」——「升」会被读成改造既有「本会话始终允许」的语义，改为「增第四选项、与既有并存」。

## §5 数字与口径

**查什么**：算术（分项和 = 总数）；口径标注（倍数、百分比、计数各指什么）；账目链（逐任务增量与总数一致）。

**怎么取证**：手算或 node 一行算每个和式；对每个「N×」倍数回查分子分母各是什么量纲；测试预估链逐段验加法。

**战例**：「1030 垃圾 + 65 损坏 + 52 真实 = 1147」验算通过；「601 行→13 行（~36×）」——36× 是**体积**（119KB/3.3KB），行数倍数是 ~46×，原文把行数放前面倍数标体积，改为分别标注。任务新增测试但预估链没动——补 ±注记或平移整链。

## §6 实施者预演

**查什么**：假装自己就是拿着文档开工的人，逐任务核对 Files：每个 Modify 的文件存在吗？每个 Test 文件是新建还是既有（有没有标注）？引用的路径、类型、函数真实存在吗？架构边界方向（若仓库有 import 规则）写反了吗？

**怎么取证**：
- `ls` / `grep -rn "符号名"` 逐个核对路径与符号。
- 新建的 Test 文件若与既有重名错觉（如 sessions.test.ts 不存在但同名源文件存在），在 Files 里标注「**新建**——现状无此文件」。
- 边界方向：文档说「经 X 函数统一」时，查 X 现在住哪个包——若在应用层而消费者在核心层，点明统一件的落位方向，否则实施者第一版就会写出边界违规。

**战例**：Task 写 `packages/core/src/session/convert.ts`，实际 deriveMessages 在 `loop/convert.ts`（session/ 下没有此文件）——照抄即错位。Task 说「harness 经 listSessions 统一」，但 listSessions 住在 apps/cli，core 不能反向 import——改为「统一件落 core 侧，apps 复用」。

## §7 消费方完备性

**查什么**：文档计划删除/改名/断流某个东西时，全仓还有谁在消费它？计划的 Files 清单覆盖全部消费者了吗？被怀疑的受害者（表面上像会受影响的模块）实际走哪条路？

**怎么取证**：
- `grep -rln "被删符号\|被删事件"` 列全部消费文件（区分源码与测试），与计划 Files 逐一对账。
- 对「可疑但可能无辜」的消费者，grep 它的实际数据来源（战例：压缩模块的 usage 锚点走运行期口 `ctx.llm.lastUsage`，不读日志 chunk——无辜，但这个结论要写进文档让实施者别再怀疑）。
- 结论双向都有价值：**全覆盖**（好消息，落名防漏改）或**有漏网**（补 Files）。

**战例**：「断流 assistant/chunk 后谁饿死」——全仓清点消费面恰为计划 Files 所列五个文件 + 一张类型表；最大嫌疑犯压缩模块经查走运行期口。清点结论整体写入 T5 注记，顺带列出存量测试改造面（grep 实测 5 个测试文件，落名进方案让实施者照单过账）。

## §8 规范对读（引文与回写目标）

**查什么**：文档声称「逐字引用」的段落真是原文吗？声称要修订/回写的目标章节，其现文确实是文档所描述的样子吗？

**怎么取证**：
- 对每处引号引用，`sed -n` 被引文档对应区域逐字比对；不一致就改引原文或去掉引号暗示。
- 对每个「将修订 §X 的 Y 条款」，先读 §X 现文确认 Y 真的在那里——**特别 grep 该契约关键词在全文的所有出现节**，防止散布多节漏掉第三处。

**战例**：方案把转述「每 append 一条 yield 一条」当 §6.7 引文——原文实为伪码 `log(chunk); yield toEvent(chunk)`；§6.7 里还藏着一处「流式 chunk 由 loop 双写」在 §6.5——初版回写清单两处都错/漏，若不抓，收官回写会去改错章节、留下自相矛盾的过时条款。

## §9 依赖复用

**查什么**：任务序列里，后面的任务会不会重造前面任务刚统一/封装的组件？

**怎么取证**：对每个「统一」「消除双实现」字样的任务，grep 后续任务的 Files 是否复用该统一件；没有明说就在后续任务加一行「复用 T<N> 的 X——不另造第 N 套」。

**战例**：T1 特意做「listSessions 统一件、消除双实现漂移」，T2 的 prune 只写「纯函数：文件清单 + mtime…」——实施者极可能写出第三套目录遍历。补注记：清单复用 T1 双层扫描。

## §10 用户视角

**查什么**：不问「实施者能不能照做」，问「落地那天终端前的用户会看到什么」——语义变化后用户可见的文案（标签、提示、报错）有人负责更新吗？语义切换的一次性可见效应（数字回落、行为突变）披露了吗？

**怎么取证**：
- 对每个「口径/语义收窄或变更」的决策，grep 用户可见文案的字符串字面量住在哪个文件——若该文件不在任何任务的 Files 里，就是**没人负责的撒谎标签**。
- 自问「用户落地当天会看到什么不同？」——若答案包括未披露的突变（累计数字清零类），在决策注记里写明可见效应与不迁移的理由。

**战例**：累计口径收窄到当前项目后，`/usage` 标签仍是「累计（全部 N 场会话）」且标签所在文件不在任何任务 Files——补 Modify 条目 + 验收断言标签口径。存量平铺会话不计入新口径导致用户数字断崖回落——补「一次性可见效应」注记（对照：别家有迁移路线，我们定案不迁移，更该写明）。

## §11 验收合规（元视角）

**查什么**：文档如果逐字引用了自家规则/硬约束（验收纪律、门禁规范、安全条款），**逐条检查文档自己的每个条目/任务是否合规**——文档最容易知法犯法。

**怎么取证**：把被引规则的判定式逐个套到文档的每个任务上。典型判定式：「用户可见功能必须有装配层测试（拿掉接线一行有测试变红）」「凡改 CLI/渲染/配置链路收尾前必须真实运行」——逐任务核对测试清单里有没有对应形态的用例、验收区有没有真实运行行。

**战例**：方案书引用了「三条硬约束 M4 起强制」，但 prune 子命令（用户可见 CLI）的 4 条用例全是纯函数级、零接线断言——违硬约束 1；改渲染的任务只有测试清单、没有真实运行验收行——违验收纪律。各补一例/一行，账目链平移。

## §12 自创值登记完备

**查什么**：计划/设计文档里**自造的语义**——魔数常量（超时、封顶、预算）、命名取舍、语义裁剪（「v1 只做 X 不做 Y」）——是否集中登记在专门的「设计空白/自创值」区块，而不是散落在任务正文里。

**怎么取证**：通读时把每个出现的自造常量与取舍记下，反向清点：它进了集中登记区吗？没进的要么补登记、要么改为引用既有定案。判断标准：**落地数月后的人只看登记区，能否解释这个值为什么存在**。

**战例**：某核心计划末轮审查发现 MAX_TOKENS、请求头版本值、120s 超时、数据预算、优先级语义等十余个自造值散落各任务——全部回收入 Global Constraints 末尾的「计划补的设计空白」并逐条给理由。散落的代价：后续里程碑回看时无档可查，改值等于盲改。

## §13 类型一致性（测试绿 ≠ 类型对）

**查什么**：计划里的接口签名/伪码，与测试用例的夹具形状是否一致——**测试在类型层面会不会根本跑不通**。

**怎么取证**：
- 对每个「测试断言 X 形状」的用例，对照接口总表/伪码的声明形状逐字段核（多一层少一层、把函数当对象调、把类型 A 的值传给类型 B 的参数）。
- 记住工具链事实：**多数测试运行器不做类型检查**（vitest 默认不 typecheck）——夹具形状错了测试可能照样绿，直到真机/构建期才爆。所以这层必须在纸面对齐，不能指望跑测试兜底。

**战例**：某核心计划终审后的外部五轴并审抓出第一硬伤：伪码把 `StreamFn` 当适配器对象调 `.stream()`，而契约里它是裸函数——typecheck 必红、测试却绿（运行器不做类型检查），「测试绿真机挂」的第四例。同批还有 `dependsOn` 传模块名而契约要求能力 key（拓扑期必降级）——契约语义误用与类型错误同源，都是**纸面形状对齐**问题。

## §14 机制推演（失败一半与回滚）

**查什么**：文档描述的每个新机制，问两个问题：**中途失败会怎样**（commit 到一半、写了一半、注册了没清理）；**回滚/逆操作会怎样**（与声明的规则顺序一致吗、会误伤新版本吗）。

**怎么取证**：
- 对每个多步骤机制（staged commit、注册-激活、双写、分步构造）逐步行推：「这步抛错，前面各步的痕迹谁回收？」
- 对每个声明的回滚/清理规则（如「先 dispose 再逆序 disposer」），与机制描述的建立顺序对**严格逆序**核对——建立是 A→B→C、清理却写成 B→C（漏 A）或 C→A（序错）都是硬伤。
- 对「边执行边记录」类设计，核对它与投影/聚合规则的时序是否自洽（记录粒度早于聚合锚点会静默丢数据）。

**战例**：某核心计划五轴并审的三处机制硬伤全在此类——激活 commit 失败只回收 services/disposers，已 push 的 command/promptSection 残留注册表且模块 dispose 永不调（staged commit 名不副实）；rollbackModule 顺序与设计规则 3 相反；loop 边执行边落 tool/call 与「附挂最近 assistant」投影规则打架，多工具回合静默丢 call。三处都是纸面可推演的，不需要跑代码。

## §15 自包含性（上下文残留检测）

**查什么**：文档引用的来源、证据、调研、实录、对照、定案过程——其支撑内容是**内联在文档里**、**有指针可溯**（底稿文档/附录/commit 历史），还是**只存在于对话上下文**？长会话里产出的文档尤其高危：模型在对话里做过对照、给过推荐理由、经历过几轮演变，写进文档的往往只有最终结论一行——上下文一压缩，结论变成无出处断言，后续读者既无法验证也无法继续深挖。

**怎么取证**：
- grep 文档中的来源类词汇：「来源/实证/调研/对照/走查/实录/挖掘/定案/参照系」，对每个命中做三分类：
  ① **内联有实质**（结论的展开就在本文或被引文档中）→ 过；
  ② **有指针**（指向底稿文档、附录、带 hash 的 commit）→ 跟过去确认指针目标真的含该内容 → 过；
  ③ **无内联无指针** → 上下文残留，修。
- 对话中产生的决策性内容自查清单：对照结论的细节（每家的参数/形态）、推荐理由的展开、多轮定案的演变序列、清单/索引类产物（如「N 项发现→处置对位」）。判定式：**「上下文压缩后重读本文，这个断言还能被理解或追溯吗？」**——不能就写。
- 修复形态三选一（按体量升序）：正文补一句展开；文档加附录/小节；新建底稿文档并在原文加双向指针。仓库惯例参照：对照调研落 `specs/` 底稿、走查实录落处置索引附录。
- 注意不要矫枉过正：原文自己明说「转写留痕于会话」且**实质要点已内联**（如缺陷列表就在文档里）的，属可接受——判据是实质内容在不在，不是原始记录在不在。

**战例**：某方案书四条来源逐条三分类后抓出三处残留——来源②「五项目调研」只剩一行「六家佐证」结论，粒度细节（16ms 合并窗口/≥3 打包/按 content block 落盘）全在对话 → 写入调研底稿新节；来源①「走查实录」无任何落盘，19 项发现散在 commit 与账本条目 → 文档加处置索引附录逐条对位；某条目注「三轮定案」但演变序列只在三个 commit → 正文补一行序列。修复后四条来源全部自包含（两处内联、两处带指针）。

## §16 源数据核对（调研/对照类文档必跑）

**查什么**：调研类文档（对照底稿、参考调研、竞品分析）里每一个**可验证的事实主张**——file:line 引用、数字、参数名、行为描述、引文——是否与真实的源（被调研的仓库/文件/数据）匹配。这类文档的内容多来自探查代理或他人转述，未经核对就是「二手断言的集合」；agent 会幻觉、行号会漂移、转述会有损。

**怎么取证**：
- 分层抽样而非全量（一份调研几十条主张，全量不经济）：按章节/项目分层，每层抽 2-4 条**最具体**的主张（优先 file:line、常量名、flag 名——越具体越易验、越易错）。
- **覆盖度按主张的决策承载分级**：给下游决策（账目条目、方案依据）当证据的主张——高覆盖乃至全验；背景性/氛围性主张——抽样即可。真实教训：一份对照底稿首轮按最低抽样过了 14 条就被宣布「源核验完成」，被用户正确质疑「这是调研文档呀」后补验 43 条决策承载主张（工具名/参数/flag/键位/文档引文）——幸而 57/57 全过，但若首轮的抽样恰好漏掉伪主张，收口判定就是假的。
- 验存在性：`ls`/`grep -rn "符号名"` 对目标仓库；验行为：读命中处前后代码段比对描述。
- **未命中 ≠ 不存在**——先换样本面再判伪：换目录（工具 flag 常在 main 入口而非 cli 子目录）、换关键词（数字常量 grep `16 \* time.Millisecond` 而非 `16ms`）、换语言习惯（Go/TS 命名差异）。两个真实案例：`--input-format` 在 main.tsx 不在 src/cli；16ms 合并窗口在 internal/event 不在 internal/agent——初查双未中、深挖双命中。
- 判伪后的处置：确认无法证实的主张**删除或标注「未证实」**，不得留无标记；行号漂移（文件在、行不对）改用「文件 + 符号名」锚定。
- 数字类主张（计数、百分比）独立复算或重跑取证命令（注意 §1 的测试文件排除条款）。

**完成标准（缺了它，本镜头会被低覆盖假完成）**：
1. 开工先列**决策承载主张清单**——grep/人工圈出「被下游引用作决策依据」的主张（对照它服务的计划书条目反查最可靠），逐条验证，**覆盖率必须 100%**；
2. 背景性/氛围性主张分层抽样即可；
3. **核验戳落盘**：核验结果（总数、关键逐字锚点、日期）写进被审文档头部——核验结论只在对话里说等于没验（§15 自我应用）；
4. 报告的【镜头覆盖】行必须写「决策承载主张 N/M 已验」——N<M 时该文档不得收口（SKILL.md 收口轮的体裁扩展条款）。

**战例**：对一份五项目对照底稿抽 14 条主张核验：12 条首查命中（file:line、常量、flag 全对），2 条初查未中——按「换样本面」纪律深挖后双双证实（flag 在 main 入口、常量在 event 包）。结论 14/14 通过，零修复——**「核查通过」本身是本镜头的正常产出之一**，与抓到错误同等有价值（它把「二手断言」升格为「已核验事实」）。**第二战例（完成标准的由来）**：该底稿二次审查时三件套全过被宣布收口，源核验却停在首轮 14 条低覆盖抽样——用户两连质疑（「做事实依据的验证了么？这个文档是调研文档呀」）后补验 43 条决策承载主张，57/57 全过。幸而零伪主张，但**若首轮抽样恰好漏掉伪主张，收口判定就是假的**——教训固化为上述四条完成标准。

## 镜头选择备忘

- 首轮固定 §1–§5（基础五镜头，收益最密）。
- 增量轮从 §6–§16 挑未用的；§11 仅当文档自引规则时适用，§7/§8 对「动契约/删东西」的文档收益最高；§12–§14 对含接口伪码与多步机制的实施计划收益最高；**§15 对长会话中产出/演化的文档必跑**（凡文档引用过调研、走查、对照、多轮定案的，收口前过一遍防上下文残留）；**§16 对调研/对照类文档必跑**（对照底稿、参考调研——主张必须抽样核验真实源，未跑 §16 的调研文档视同未审）。
- 长文档（~2000 行+）优先**分轴并审**（见 SKILL.md 流程节），轴内再挑镜头。
- 收口前必跑**终验三件套**（决策锚点全覆盖 / 交叉引用全解析 / 术语零残留——见 SKILL.md 流程节）；三件套过了才按铁律 3 收口，把断言强度留给实施期。
- 每轮换镜头时读上一轮报告确认已用集合。
