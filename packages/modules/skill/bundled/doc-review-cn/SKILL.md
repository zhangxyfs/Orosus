# 技术文档深度审查（多镜头）

沉淀自三场真实战役：一份实施方案书七轮实审（68 处修复、四个契约级错误）、一份核心计划十一轮复审（末轮外部五轴并审抓出 6 处执行硬伤）、一份设计主文档八轮审查加终验（含一次整文件重写静默覆盖三条定案的结构事故）。核心信念只有一条：**文档审查不是「再读一遍、读仔细点」，而是换镜头**——同一份文档，从不同的观察角度各看一轮，每个镜头只负责它看得见的那类问题。

## 何时用 / 何时不用

**用**：计划书、实施方案、设计文档、规格、调研底稿、README——在大改之后、定稿或过审之前、或用户连续追问「还有问题吗」时。**调研/对照类文档在刚写完的当下就应触发**（产出调研的那个会话直接自跑 §16 源数据核验——不要等用户想起来下审查指令，那之间的窗口期伪主张在自由流通）。
**不用**：代码变更审查（用 code-review 类 skill）；纯错别字顺稿（直接改）；仍在快速起草、内容还会大动的草稿（等稳定再审）。

## 三条铁律

1. **取证先于指控**。每一项发现必须先核实才允许写进结论：grep 源码、读被引文档原文、`git log` 查日期、跑测试数。「文档说 X」不等于「X 是事实」。实战记录：一轮指控五处决策号引用，取证后发现**全部是伪引**（从压缩对话记忆里带出、从未核验）；另一轮怀疑日期标错，`git log` 取证后确认**虚警**（工作确实发生在标注当天深夜）——两个方向的反例都证明了这条铁律的价值。
2. **修复即落盘，且双向校验**。问题当场修进文档（带来源与日期注记），不留「建议清单」让用户自己搬。修复一批后做两个方向的机械校验：**新模式零残留**（grep 旧模式，期望零命中）与**旧内容零丢失**（`git diff` 逐块确认改动只增不删——整段/整文件重写是静默覆盖既有定案的高危操作，真实事故：一次重写丢了三条已定案条款而历轮自检毫无察觉，因为大家只查「新的落位没有」；重写前先 `git diff HEAD` 圈定既有内容）。
3. **诚实收敛**。每轮报告发现密度并累计。当镜头池用尽或某轮零实质发现，明说「纸面审查已到收益递减点，剩余镜头（断言强度、FMEA、并发时序）对着纸面是空的，属实施期 TDD/runbook 的主场」，然后建议收口开工。不硬凑发现，不为延续审查而审查。

## 流程

### 首轮（用户说「深度审查，不要错过任何问题」）

默认跑基础五镜头：**事实时效、结构、编号引用、语言、数字**（详见 `references/lenses.md` §1–§5）。这是任何文档的第一遍，收益最密。若用户明说「全量」，把全部适用镜头一次跑完，按镜头分批执行。

### 增量轮（用户说「再审查 / 换个角度 / 还有吗」）

从未用镜头池挑选。优先级参考：**消费方完备性 > 规范对读 > 实施者预演 > 用户视角 > 依赖复用 > 验收合规**（最后一条仅当文档自引了规则/硬约束时适用）。判断已用镜头：读自己上一轮的报告与 commit 信息。

### 长文档分轴并审（文档超过 ~2000 行时强烈建议）

单遍通读长文档会疲劳漏检。按文档自身结构切轴、每轴独立深挖一轮（参考某核心计划的五轴法：契约一致性轴 / 核心机制前半轴 / 后半轴 / 模块与装配轴 / 引用与外部文档轴）。切法随文档形态定——原则是**每轴够小、能一口气深挖**，轴间允许重叠（重叠处常是双面责任区）。

### 收口轮（镜头用尽或零发现时，不是直接结束——先跑终验三件套）

机械化收尾，比人工终读可靠（某设计文档终验首次执行时三查全过、无 A/B 类发现，此后成为固定工序）：

1. **决策锚点全覆盖**：文中出现的每个决策号/规则号，逐号到登记册 grep，全命中才收口；
2. **交叉引用全解析**：文中每个 §x.y / 章节引用，拉被引文档目录逐一对位（可 grep 提取后批量核）；
3. **术语与命名零残留**：grep 已废弃的旧名/别名/曾用名，期望零命中。

**体裁扩展（必须套用）**：调研/对照类文档的收口门 = 三件套 **+ §16 覆盖达标**（决策承载主张 100% 已验 + 核验戳已落文档——详见 lenses.md §16 的完成标准）。三件套全过但 §16 未达标的调研文档**不得收口**——真实事故：一份对照底稿三件套全过被宣布收口，源核验却停在 14 条低覆盖抽样，被用户两连质疑后补验 43 条（幸而全过，但收口判定此前是虚的）。

三件套（含体裁扩展）过了才按铁律 3 宣布收敛。

### 每轮收尾（固定动作）

1. 应用修复 + 残留扫描（grep 旧模式 = 零命中）；
2. 若仓库有门禁（测试/lint/typecheck 等），全部跑一遍，**只以退出码判定**；
3. commit，信息写明轮次、镜头、发现数与最重要的发现；
4. 向用户报告——格式见下。

## 报告格式

```
第 N 轮（镜头名）完成：X 处修复，提交 <hash>，门禁全绿。

【镜头覆盖】本轮跑过的镜头清单；调研类必含 §16 覆盖声明——「决策承载主张
  N/M 已验」（N<M 时不得宣布收口；本行必填，防止镜头被静默跳过）。
【最重要发现】一句话 + 为什么重要 + 修了什么。
【其余修复】按镜头分组，每条标严重度：A = 矛盾/执行硬伤（照做必错、契约冲突）；
  B = 语义缺口（欠指定、歧义、过时主张）；C = 小项（措辞、注记、账目微调）。
【核查通过项】本轮查过但没问题的（让用户知道覆盖面，而不只是什么坏了）。
【累计】N 轮 X 处修复；发现密度趋势；是否建议收口（收口前终验三件套——含体裁扩展——跑了吗）。
```

先结论后细节；「核查通过项」必须有——它是用户信任「没发现 ≠ 没查」的唯一依据。A/B/C 分级源自多轮实战的收敛分类：A 类不修完不许开工，B 类开工前须定案，C 类随手修。

## 镜头速查表

| 镜头 | 一句话 | 典型捕获（真实战例） |
|---|---|---|
| 事实时效 | 文档声明的事实现在还真实吗 | 基线 commit/测试数过时；文档引用了比自己声明的基线更新的提交（自相矛盾） |
| 结构 | 编号/标题/登记完备且一致 | 有 Part II–V 却没有 Part I；节标题漏掉后补的条目；同一项在「范围内」和「范围外」两处登记 |
| 编号引用 | 每个编号、缩写、引文都可解析 | 决策号与登记册对不上（伪引）；§节号指向错误章节；缩写首次出现未定义；两套编号体系撞车（同文 B6 两义） |
| 语言 | 悬空指代与语义歧义 | 指向已删除文档的标记；「升级」被读成改造既有语义而实为新增选项 |
| 数字 | 算术与口径 | 分项之和 ≠ 总数；倍数口径张冠李戴（体积倍数标在行数上） |
| 实施者预演 | 拿着文档照抄能开工吗 | 引用的文件路径不存在；新建文件误作就近修改；架构边界方向违规（如 core 反向 import apps） |
| 消费方完备 | 被删/被改的东西还有谁在用 | 全仓 grep 后发现计划 Files 清单恰好全覆盖（好消息也要落名进文档）或漏了隐藏消费者 |
| 规范对读 | 引文是原文吗？回写目标真实吗 | 转述冒充逐字引用；「修订 §X」的 §X 里根本没有所声称的内容（漏了 §6.5 这类第三处） |
| 依赖复用 | 后面的任务会不会重造轮子 | 后任务重写前任务刚统一掉的组件（第三套目录遍历） |
| 用户视角 | 用户可见的行为诚实吗 | 标签文案与新语义不符（口径收窄后标签撒谎）；语义切换的一次性可见效应未披露（累计数字断崖） |
| 验收合规 | 文档自己守不守它引用的规则 | 用户可见功能没有装配层测试；改渲染却没有真实运行验收 |
| 自创值登记 | 自造的常量/语义集中登记了吗 | 计划里散落的超时值/封顶常量/命名取舍未进「设计空白」——落地时无档可查 |
| 类型一致性 | 伪码/接口与测试夹具形状一致吗 | 测试绿但 typecheck 必红（vitest 不做类型检查——「测试绿真机挂」） |
| 机制推演 | 失败一半/回滚时会怎样 | commit 失败残留注册表；回滚顺序与声明的规则相反 |
| 自包含性 | 引用的来源/证据真写进文档了吗 | 文档说「五家公约数」但对照细节只在对话上下文；来源引「走查实录」但实录无处可查——压缩后断言变无出处 |
| 源数据核对 | 调研主张与真实源匹配吗（file:line/数字/行为，抽样核验） | 对照底稿引用的文件不存在、常量名是幻觉、行号漂移——**调研类文档必跑，未跑视同未审** |

每个镜头的**详细取证手法与完整战例**读 `references/lenses.md`——动手前必读对应小节。

## 仓库纪律适配

本 skill 不硬编码任何仓库的规矩。开工前先探明目标仓库的：门禁命令（package.json scripts 等）、文档权威源（决策登记册、主设计文档的位置）、commit 纪律（是否每修复一 commit）。文档若引用了该仓库自己的规则文档，**验收合规镜头**自动适用。

## 文档生命周期适配（先判断再选镜头）

动手前先判断文档处于哪个生命周期，镜头价值排序完全不同：

- **活文档**（待审/执行中，如待开工的计划书）：全部镜头适用，按「流程」节的默认排序。
- **调研/对照类文档**（底稿、参考调研、竞品分析）：**§16 源数据核对必跑**——每个可验证主张（file:line、数字、行为）抽样对照真实源核验；未跑 §16 的调研文档视同未审。其余镜头按需。
- **已收官/历史文档**（执行完毕的计划、存档备忘）：**事实时效与编号引用**占绝对主导——查状态行是否还挂着「待审」、前置条件/「X 未落地」类主张是否已被后续里程碑推翻、引用的基线与行号锚点是否需要注记。实施者预演/依赖复用/消费方镜头基本失效（代码早已演进，路径对不上是常态而非缺陷——除非头部已声明路径映射）。修复原则：**只改状态行与过时主张，加带日期的修订注记（复核注 + 指向现行事实的锚点），不重写历史记录本体**；有变更记录表的文档在表里加一行而非涂改旧行。
- **草稿**：别审（见「何时不用」）。

判据：状态行的措辞 + git log 里该方案对应的收官 commit 是否存在。
